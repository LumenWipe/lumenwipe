This page defines what "healthy" means for the LumenWipe API and the close flow. It lists each service level indicator (SLI), how it is measured, the objective (SLO) proposed for it, what happens as the error budget is spent, and when an alert fires.

## Status

- **Every target on this page is a proposal.** A target is confirmed or changed only after 30 days of measurement exist for its indicator.
- **No figure is published before then.** No attainment, uptime or latency number for these indicators appears in public until 30 days of measurement back it.
- **The burn-rate alerts are defined, not automated.** The API has no metrics pipeline yet (metrics and tracing are deferred). Until it does, the indicators are read from the sources named below, and none of them pages anyone. The monitors that do alert today are listed in the [monitoring plan](/monitoring-plan).

Every objective is evaluated over a **28-day rolling window**.

## What one instance and one provider support

The API runs as a single Cloud Run service in one region, with one instance at most and none kept warm. A cold start or a regional incident takes the API down, with no second instance or region to take over. RPC and Horizon-compatible reads can fail over along an ordered provider list (see [Provider failover](/architecture#provider-failover)), but a request stays on the provider it pinned, and the API refuses with a retryable `503` once the list is exhausted. DeFi position detection, Soroban token quotes and the explorer each depend on a single provider. Over 28 days, 99.9 percent availability allows 40 minutes of total downtime, which this setup cannot honestly promise. The starting availability target is 99.5 percent, which allows about 3 hours 22 minutes. Raising it first needs a warm instance ([#493](https://github.com/LumenWipe/lumenwipe/issues/493)), a measured concurrency limit, and a second provider for the reads that have one today.

The freshness limits follow the cadence the monitors run at today: once an hour, or once a day. The extra 15 minutes and 1 hour leave room for scheduler delay. A 20-minute limit would need a monitor that runs every 15 minutes or more often, and none does today. As [#278](https://github.com/LumenWipe/lumenwipe/issues/278) adds monitors, each is added here at its own cadence.

## Error-budget policy

The error budget is the share of the window an objective allows to fail: 0.5 percent of requests for availability, 5 percent of analyses for latency, and so on. Every failure spends it, including a dependency outage that fails closed.

- **Half the budget spent.** Changes that put the indicator at risk, such as a new close operation, a provider change or a deploy configuration change, ship one at a time, each with its rollback written down. The maintainers look at what spent the budget and open an issue for each cause they find.
- **The whole budget spent.** Only changes that restore the indicator, and security fixes, ship until the 28-day spend falls back under the budget. Any single event that spent at least a fifth of the budget gets a written review. If a provider outage spent the budget, the fix is on the provider side (a second provider, or a different one), not a freeze on unrelated work.

## Burn-rate alerts

A burn rate is how fast the budget is being spent: a rate of 1 spends exactly the whole budget over the 28 days. Each alert needs both of its windows over the rate, so it fires quickly and stops once the problem ends.

| Alert     | Burn rate | Long window | Short window | Budget spent when it fires | Goes to                                                                                    |
| --------- | --------- | ----------- | ------------ | -------------------------- | ------------------------------------------------------------------------------------------ |
| Fast burn | 14.4      | 1 hour      | 5 minutes    | About 2 percent            | A page: a post that pings `@everyone` in the maintainers' channel                          |
| Slow burn | 6         | 6 hours     | 30 minutes   | About 5 percent            | A ticket: an assigned GitHub issue and one post, with no ping, in the maintainers' channel |
| Slow burn | 1         | 3 days      | 6 hours      | About 11 percent           | A ticket, as above                                                                         |

The maintainers' channel is the one the monitor workflows already post their findings to, through the `DISCORD_MONITORS_WEBHOOK_URL` repository secret. A ping there is already reserved for findings that need someone at once (see [the monitoring plan](/monitoring-plan#how-the-live-ones-run)). A separate alert channel was considered and not built ([#486](https://github.com/LumenWipe/lumenwipe/issues/486)), because this one already reaches the team.

**A dependency outage that fails closed never pages.** When the API refuses with `503 service_unavailable` because a provider is unavailable or too slow, nothing unsafe was built, and paging a person cannot bring the provider back. That spend still counts against the budget, but at any burn rate it opens a ticket and nothing more.

## Latency baseline

The baseline for the analyze threshold comes from the [latency lab](https://github.com/LumenWipe/lumenwipe/blob/main/tools/lab/README.md). The lab measures cold and warm p50 and p95 for each scenario, against the production API (black box) and against a local API process that reads the same public providers (white box). A local white-box run has been recorded. The production black-box run is pending a measured run. Lab results are kept outside this repository and are not published here. The analyze threshold is set from them once 30 days of production data exist to check them against.
