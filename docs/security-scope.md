LumenWipe ends every close in an irreversible merge of a user's funds, so a small set of paths decides whether
that merge goes where the user asked. This page lists them by path, says why each is sensitive, and names the
owner role and the review a change there needs. It is the path list behind the closer-review rule in
[CONTRIBUTING.md](https://github.com/LumenWipe/lumenwipe/blob/main/CONTRIBUTING.md). The
[threat model](/threat-model) explains the threats these paths answer, and the [invariant register](/invariants)
says which of their guarantees a test proves.

`bun run check:docs` fails the build when a path below no longer exists, so a move or a rename has to update this
page in the same pull request. It does not check that the list is complete: a new sensitive file is added here by
the pull request that creates it.

## Owner roles

Roles, not people, so the page survives absences. A maintainer may hold more than one.

- **Verification owner**: the browser and playground trust anchors, client-side signing and its orchestration,
  the SDK's close runner, and the latency lab's local signing. Everything that decides what a user signs.
- **API owner**: transaction construction, the account reads `verify()` relies on, the two server-side Stellar
  signing keys, authentication and key issuance, and the contract and exchange registries.
- **Infrastructure owner**: the web server's proxy and Content Security Policy, CI, deploy and dependency
  configuration, and the documents and checks that define this scope.

## The closer-review rule

A pull request that touches any path above:

1. Says so in its description and names each group it touches.
2. Gets a security review of its diff before it is opened, recorded in the description: what was checked and
   what was found. Maintainers run their security review tooling for this; an outside contributor asks a
   maintainer to.
3. Gets an approving review from the owner of each group it touches, or, for a group whose owner is the
   author, from another maintainer. One maintainer holding several roles can approve for all of them. When no
   other maintainer is available, the pull request waits. The approver reads the whole diff of each group, not
   only its tests.
4. When it adds a close operation, a signing key, an adapter, a surface or an app boundary, updates the threat
   model and the invariant register in the same pull request.

The rule is applied by the author and the reviewer. As of 2026-10-13, GitHub does not enforce it: the repository
has no `CODEOWNERS` file and requires no approving review count, so the required CI checks are the only automatic
gate.

## Registry signing keys

The exchange registry is published with a detached Ed25519 signature (`apps/api/src/config/exchange-registry.sig.json`, served as `signature` beside the registry). The clients (`apps/web` and `@lumenwipe/verify`, from the one source `apps/web/lib/exchange-registry/trust-roots.ts`) verify it against these two public keys. Either verifies: the second is a backup, not a quorum.

| Key     | Public key                                                 |
| ------- | ---------------------------------------------------------- |
| Primary | `GAKGKRCTIPJIFS4UAL6TZEXW3ZUUYBFBPBAVNG37NKILQQ5ZSW3VGDTK` |
| Backup  | `GAOXVNB4UHWUOXDLSQXTPUJUZWRHKO35ZP5P5XZNPESMEIPUL3X66PDD` |

The secrets are held offline by maintainers and never on the API host. A test fails when this table and the source disagree.

**What a signature unlocks.** An unsigned served registry can only make a client stricter. A signature that verifies lets the registry add an exchange that needs the shared relay account, and nothing more: it cannot change a bundled entry, a memo type or a network scope. It decides whether the mediated shape is allowed; it does not vouch for the account a mediated close merges into. See [the threat model](/threat-model#5-surface-4a-backend-signing-key-mediator-co-sign).

**What is signed.** The bytes are the label lumenwipe.exchange-registry.signature.v1 (a fixed ASCII string), a newline, and the canonical JSON (keys in UTF-16 code unit order, no whitespace, integers only) of `{ format, issuedAt, registry, sequence }`, where `registry` holds `version`, `lastVerified`, `validUntil`, `source` and `entries` exactly as served. The envelope is `{ format: 1, sequence, issuedAt, signature }` with the signature in base64. A client believes it only when a pinned key verifies it, its `sequence` is at least the sequence of the registry bundled in the client (a client never accepts an older signed registry), `validUntil` has not passed (the whole day counts), and `issuedAt` is no more than a day ahead of its clock. A client with a fast clock stops believing a signature early and a slow clock keeps believing it as long as it is slow, bounded by `validUntil`; a missing, truncated, forged, stale or otherwise failing signature leaves the registry unsigned, exactly as served registries behaved before signatures. The conformance vectors are `packages/verify/vectors/registry-signing-v1.json`.

**Signing procedure.** After a registry change is reviewed, a key holder runs, from the repository root:

1. Pipe the secret seed into `bun packages/verify/scripts/sign-registry.ts`. The script reads the seed from standard input only, refuses to prompt, never prints it, requires its public key to be one of the pinned keys, signs with a sequence one above the committed one, and writes the signature file.
2. `bun run --filter '@lumenwipe/verify' vectors`, which refreshes the vector made with the production key.
3. Commit the signature and the vectors. CI runs `bun packages/verify/scripts/sign-registry.ts --check --base HEAD^1`: it fails when the signature does not verify under the pinned keys for the committed registry, or when the registry changed against the parent commit without a higher sequence.

**Rotation.** Drop a key from `REGISTRY_SIGNING_KEYS` in a release; clients on that release no longer believe signatures made only by it. To rotate without a gap, sign with the surviving key first, release without the old key, then add the replacement in a later release. A client on an older release keeps trusting a dropped key until it upgrades, so a suspected compromise is also a `@lumenwipe/verify` release and a note for integrators.

## Out of scope

These carry no fund path or key, so ordinary review applies:

- The playground's UI: `apps/playground/app/` and `apps/playground/components/`, except `apps/playground/app/api/`
  and the files listed above.
- The marketing pages: `apps/web/app/(marketing)/` and `apps/web/app/(marketing-es)/`.
- The docs site under `docs/`, except the pages listed above. For other pages, review covers their claims;
  `bun run check:docs` only confirms that the files, symbols and tests they name exist.
