The LumenWipe API reads on-chain state and builds every unsigned transaction of a close. Your code verifies, signs, and submits. A private key never reaches the API.

The endpoint pages in this section are generated from the API's OpenAPI document. Prefer a typed client? The `@lumenwipe/sdk` package wraps these endpoints.

## Base URL

```text
https://api.lumenwipe.com
```

Most routes take the network in the path, either `mainnet` or `testnet`, for example `/v1/testnet/close/plan`. Any other value returns `400 invalid_network`.

## Versioning

Every integrator route lives under `/v1`, for example `/v1/testnet/account/G...`, `/v1/config/exchange-registry` and `/v1/integrator/keys`. A breaking change to a request or response gets a new prefix (`/v2`) instead of changing `/v1`. `GET /` and the health routes are operational and stay unversioned. The operator-only key administration routes under `/admin` are not part of the public API and are not versioned.

Paths without the prefix, such as `/testnet/account/G...`, `/{network}/mediator/sign`, `/config/exchange-registry` and `/integrator/...`, are deprecated aliases. They answer exactly as their `/v1` path does, with the same authentication and the same rate-limit budget, and add three headers:

| Header        | Value                                                                                                   |
| ------------- | ------------------------------------------------------------------------------------------------------- |
| `Deprecation` | `@1794182400`, the date the alias was deprecated (2026-11-09), in RFC 9745 form.                        |
| `Sunset`      | `Tue, 01 Jun 2027 00:00:00 GMT`. After this date an alias may stop answering.                           |
| `Link`        | The `/v1` path to call instead, as `rel="successor-version"`, and this section, as `rel="deprecation"`. |

The deprecated paths are not listed in the endpoint pages. Move to the `/v1` path before the sunset date.

## Authentication

Send your API key as a bearer token:

```bash
curl https://api.lumenwipe.com/v1/testnet/account/G... \
  -H "Authorization: Bearer $LUMENWIPE_API_KEY"
```

`GET /`, the health routes, and `GET /v1/config/exchange-registry` need no key. Everything else does. [Get an API key](https://lumenwipe.com/api-keys) with the self-service page.

<Warning>
  Keep the key on your server. A browser application should call the API through its own backend, as
  the LumenWipe web app does.
</Warning>

### Self-serve keys

You manage your keys by signing in with a Stellar wallet: `POST /v1/integrator/auth/challenge` returns a message to sign, and `POST /v1/integrator/auth/session` exchanges the signature for a session token that lasts 30 minutes. Sign in again when it expires. The session token only manages keys; it is not an API key.

- A wallet holds at most 5 active keys. Creating a sixth answers `409 key_limit_reached`; revoke one first.
- `POST /v1/integrator/keys` takes an optional `label` (1 to 64 characters) and an optional `networks` list (`["testnet"]`, `["mainnet"]` or both). A key without `networks` works on every network.
- A key with `networks` is refused with `403 key_network_not_allowed` on any other network, and on any keyed route that takes no network. The request does no work before it is refused. The label and networks cannot be changed later, and rotating a key keeps them.
- Each key has its own rate-limit budget (see [Rate limits](#rate-limits)).
- `GET /v1/integrator/keys` returns each key's `label`, `networks` and `lastUsedAt`. `lastUsedAt` is written at most once a minute, so it can trail the key's real use by about a minute, and stays `null` until a use has been written.
- Each listed key also carries `usage`: its successful requests today and over the last 30 UTC days, today included, and the requests refused with `429` over the same 30 days. A key's `429` count is written at most once a minute and can trail by that much. The top-level `usage` is still the wallet's total across all its keys. Counts survive a restart; `usage` is `null` when they cannot be read.

## Errors

Every error uses the same envelope, whichever endpoint produced it:

```json
{
  "error": {
    "code": "destination_not_acknowledged",
    "message": "Plain-language explanation.",
    "details": {}
  }
}
```

Branch on `code`. The `message` is written for people and may be reworded, and `details` appears only when there is more to say. Responses never include stack traces or raw SDK errors.

| Status | Code             | Meaning                                                                                                                                  |
| ------ | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 400    | `bad_request`    | The request is malformed. Specific codes such as `invalid_network` and `invalid_body` name the problem.                                  |
| 401    | `unauthorized`   | The API key is missing or invalid.                                                                                                       |
| 404    | `not_found`      | The route does not exist. Specific codes such as `account_not_found` name a missing account.                                             |
| 409    | `quote_drifted`  | A conversion route disappeared between planning and building. Plan again.                                                                |
| 409    | `state_changed`  | The account changed between the API's read and its build, or during an account read. Nothing was submitted. Plan or read again.          |
| 422    | specific code    | The request is valid but cannot be built, for example `destination_not_acknowledged` when an unrecognized destination was not confirmed. |
| 429    | `rate_limited`   | Too many requests. Wait and retry.                                                                                                       |
| 500    | `internal_error` | Something went wrong on the server. Retry.                                                                                               |

## Request ids

Every response, success or error, carries an `X-Request-Id` header. An error body repeats it as `error.requestId`. The API generates the id for each request and ignores any value a caller sends. Quote it when you report a problem, so it can be matched to the log line for that request. What the logs hold is described in [Logging and privacy](/reference/logging-and-privacy).

## Rate limits

Requests are limited per API key, and per client IP when a request carries no key. One budget covers every endpoint. The default is 120 requests per 60 seconds. A key issued through the self-serve flow can carry its own limit and window, which replaces the default for that key only. Rate limiting applies before authentication and before the request body is read, so requests without a valid key, unknown routes and malformed bodies count against the budget too. The service index, the health checks and the documentation pages are not limited.

Every limited response carries the state of the budget:

| Header                | Meaning                                                                             |
| --------------------- | ----------------------------------------------------------------------------------- |
| `RateLimit-Limit`     | Requests allowed in the current window.                                             |
| `RateLimit-Remaining` | Requests left in the current window.                                                |
| `RateLimit-Reset`     | Seconds until the window resets. On a `429`, seconds until the key is served again. |
| `Retry-After`         | Seconds to wait before retrying. Sent on every `429` and every `503`.               |

Exceeding the limit returns `429 rate_limited`. The legacy `X-RateLimit-Limit`, `X-RateLimit-Remaining` and `X-RateLimit-Reset` headers carry the same values and are deprecated: they are sent for one more release and then removed, so read the `RateLimit-*` names.

A single `runClose` over a multi-round account shares this budget with any polling you do, so size your concurrency from `RateLimit-Remaining` rather than guessing.

## Retrying each endpoint

A `504` from `submit` means the outcome is unknown, not that the transaction failed. Compute the hash from the envelope you signed, then call `GET /v1/{network}/transactions/{hash}`. Honor `Retry-After` wherever it is sent.

| Endpoint                                                                           | Safe to retry                           | Retry after                                                                                               | Never retry                                                                                        |
| ---------------------------------------------------------------------------------- | --------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `GET` reads, including `transactions/{hash}`, `close/status` and `close/delivered` | Network error, 429, 502, 503, 504       | `Retry-After`, else a few seconds                                                                         | A `400`                                                                                            |
| `POST close/plan`, `close/batch-plan`, `close/transactions`                        | Network error, 429, 503                 | `Retry-After`. Each call re-reads the account                                                             | A `4xx` before the cause is fixed                                                                  |
| `POST submit`, same signed envelope                                                | Only after a lookup by hash, or a `429` | About one ledger. The API checks the hash first, so a confirmed envelope answers `200` with the same body | `invalid_*` and `422 submit_rejected`: the network refused it, so build and sign a new transaction |
| `POST {network}/mediator/sign`                                                     | Network error, 429, 503                 | `Retry-After`                                                                                             | A `4xx`. Co-signing a replaced transaction spends the relay account's sequence                     |
| `POST {network}/fee-bump/sponsor`                                                  | 429, 503                                | `Retry-After`                                                                                             | `sponsorship_budget_exhausted` before the next UTC day                                             |

`POST submit` for an envelope that already confirmed answers `200` with the same `hash` and `ledger`, however many times it is sent. The check is by hash through RPC, so it holds for as long as the RPC provider retains the transaction.

## Following a close

Use polling. `GET /v1/{network}/close/status?source=` reads live state and keeps nothing between calls, so it needs no session. It answers one of four phases.

| Phase            | Meaning                                                                                               |
| ---------------- | ----------------------------------------------------------------------------------------------------- |
| `open`           | The account is on the ledger with sub-entries or sponsorships. `remaining` counts them.               |
| `ready_to_merge` | The account is on the ledger and the ledger counts nothing left on it.                                |
| `closed`         | The account is absent and the last operation in its history is a merge.                               |
| `unknown`        | The account is absent and no merge is in the history this provider serves. It may never have existed. |

`remaining` does not cover claimable balances or DeFi positions, which the ledger does not count on the account. A full plan covers those. `closed` is informational: it does not say which transaction merged the account, so confirm a close by the hash of the merge you signed, never by this phase.

Each call costs one request against your key's rate limit, and upstream one RPC read, plus one Horizon read when the account is absent. Poll an account no more often than every 15 seconds: a ledger closes about every 5 seconds, and nothing changes faster than your own transactions. At the default 120 requests per minute that follows about 30 accounts at once, with the rest of the budget spent by `RateLimit-Remaining` on the close itself.

There are no webhooks. Delivering one needs subscriptions, delivery state and signing secrets kept per close, and the API keeps nothing per close. See [the design note](https://github.com/LumenWipe/lumenwipe/blob/main/docs/architecture.md#following-a-close-from-outside).

## The XLM a close delivered

Once the transactions of a close are confirmed, `GET /v1/{network}/close/delivered?destination=G...&hashes=<hash>,<hash>` reports the XLM each one delivered to the destination. Pass 1 to 20 distinct hashes, comma-separated. Ask only after `transactions/{hash}` reports `confirmed`.

The amount is read from the ledger's own result for each transaction: RPC first, then Horizon when RPC no longer holds it. It is never estimated from the plan. Only two things count:

- the balance a successful merge into the destination carried, as the merge's result reports it;
- for a close routed through the relay account, the successful native payment to the destination from the account a merge earlier in the same transaction went into, at most once per merge and never more than that merge carried.

XLM that reached the destination by any other operation, such as a path payment or a payment without that merge, is not counted, and neither is any asset other than XLM.

Each hash gets an entry, in the order asked. An entry that cannot be read as delivered is `unavailable` with a `reason` and no amount:

| Reason        | Meaning                                                                                                     |
| ------------- | ----------------------------------------------------------------------------------------------------------- |
| `not_found`   | Neither RPC nor Horizon holds the hash. It may be unknown, still pending, or older than the providers keep. |
| `failed`      | The transaction failed, so it moved nothing.                                                                |
| `no_delivery` | It confirmed without a merge into the destination or a forward of a merged balance to it.                   |

`totalStroops` is present only when every entry is `delivered`, so a missing amount never reads as zero. A fee-bump answers for its outer or its inner hash. A provider that answers with a different transaction, or one from another network, is a `503`, never an amount. One call is one request against your key's rate limit, however many hashes it carries, and costs up to two upstream reads per hash.

## The close loop

A close is a sequence of calls. The API keeps no state between them, so a close can resume after an interruption.

1. `POST /v1/{network}/close/plan` returns the full plan and any decisions you must answer.
2. `POST /v1/{network}/close/transactions` returns the next unsigned transactions. Verify and sign them.
3. `POST /v1/{network}/submit` submits the signed transaction. If the outcome is unknown, resolve it with `GET /v1/{network}/transactions/{hash}`.
4. Repeat from step 2 while the response says another call is required.

Each entry of the plan's `decisionPoints` carries a `subject` whose shape depends on its `type`. For an `asset_disposition` on a convertible classic asset, `subject.quote` is the swap quote, in stroops of XLM, priced at the balance the step will move:

| Field              | Meaning                                                       |
| ------------------ | ------------------------------------------------------------- |
| `estimatedReceive` | The XLM the route is expected to deliver.                     |
| `minAmountOut`     | The least XLM the route may deliver once slippage is applied. |

The quote is display data. To hold the conversion to a figure the user saw, send it as the convert answer's `params.minAmountOut`; `close/transactions` refuses a route that no longer clears it with `quote_drifted`. `quote` is absent when no route exists, and for a balance a position's exit has yet to pay in.

For exchange destinations, `POST /v1/{network}/mediator/sign` co-signs the mediator's forward payment. To plan several accounts at once, use `POST /v1/{network}/close/batch-plan`. See [how a close works](/guides/how-closing-works) for the flow from a user's side.
