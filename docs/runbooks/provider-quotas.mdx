The API reads from providers it does not run. Each one limits how fast or how much the API can ask, and a provider that refuses ends the request with a retryable `503` (see [Provider outage](/runbooks/provider-outage)). This page records what each provider publishes, the monthly request budget the API keeps under it, and the alerts that fire at 70 percent of a budget.

## Where the counts come from

The API counts every HTTP attempt to each upstream, retries included, by network: `rpc`, `horizon`, `paths`, `defi` (OctoPos), `indexer` (StellarIndex), `soroswap` and `xbull`. The counts are written once a minute to `upstreamUsage/{YYYY-MM-DD}` in Firestore ([Upstream metrics](/monitoring-plan#upstream-metrics-and-dependency-health)). A request whose caller named no network is stored under `unknown`. The budget check charges it to that upstream on every network, so an alert can come early but never late.

## Quotas and budgets

Budgets are in [`apps/api/src/config/upstream-budgets.json`](https://github.com/LumenWipe/lumenwipe/blob/main/apps/api/src/config/upstream-budgets.json). Upstreams that spend one quota share one budget: `horizon` and `paths` go to the same Horizon host, and one Soroswap or StellarIndex key serves both networks.

Each budget follows one of three rules:

- **A published rate limit**: a quarter of that rate, sustained over a 30-day month. Rate limits bind on bursts, so the average stays well below the ceiling.
- **No published limit**: 20 times the busiest month observed so far (November 2026, through the 19th), with a floor of 1,000 requests. An alert then means traffic grew enough to agree a plan with the provider before relying on an unpublished limit.
- **Never called on that network**: 0. A single request is then a finding.

Three budgets also carry a fixed allowance for the status probe, `GET /health/user-path` ([Status page probes](/monitoring-plan#status-page-probes)). It is not a rule of its own: it is a known, constant load added on top of the budget its rule gives, so that the 70 percent alert keeps measuring user traffic. The probe runs at most once every 300 seconds while it passes, which is 8,640 runs in a 30-day month, and one run was measured on 2026-11-24 at 27 Stellar RPC, 8 Horizon and 2 OctoPos requests, with 4 StellarIndex requests taken from the production access log of an analysis:

| Budget                    | Rule gives | Probe allowance      | Budget  |
| ------------------------- | ---------- | -------------------- | ------- |
| Stellar RPC, mainnet list | 100,000    | 27 x 8,640 = 233,280 | 333,280 |
| OctoPos                   | 4,000      | 2 x 8,640 = 17,280   | 21,280  |
| StellarIndex              | 6,000      | 4 x 8,640 = 34,560   | 40,560  |

Horizon on mainnet needs no allowance: 8 x 8,640 = 69,120 requests fit inside the 648,000 its published rate gives. While the probe fails it runs once every 60 seconds instead, so a long outage spends the allowance up to five times faster, and an alert during one is expected. Change the probe's period, fixture or steps and these three numbers change with it.

A provider added to `STELLAR_RPC_<NET>` or `PATH_ROUTING_API_<NET>` brings its own quota. Before adding one, check that its published limit is at least the budget of the list it joins, and record it here.

## Alerts at 70 percent

- **Upstream requests.** The API checks its own budgets, with no credential beyond the one it already writes the counts with. After it writes the counts, at most once an hour per instance, it sums this month's `requests` and logs one `WARNING` line for each budget at or past 70 percent. The line has the fixed message `upstream request budget at 70 percent`, with `provider`, `networks`, `upstreams`, `percent`, `used` and `budget` as fields. The log-based metric `upstream_budget_threshold` counts those lines, and an alert policy on it notifies the maintainers while any line arrives. A budget past 70 percent logs again every hour the API takes traffic, so the alert stays open until the month resets or the budget is raised. A check that cannot read the counts logs `upstream_budget_check_failed` and tries again an hour later.
- **Cloud spend.** Each budget on the billing account alerts at 70 percent of its amount, among its other thresholds. The `billing` check of the [migration check](/runbooks/restore-api-keys#migration-check) fails when no budget alerts at 70 percent.

## When an upstream alert fires

1. Read the lines that fired it:

   ```bash
   gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="lumenwipe-api" AND jsonPayload.message="upstream request budget at 70 percent"' --freshness=2h --format='value(jsonPayload.provider,jsonPayload.percent,jsonPayload.used,jsonPayload.budget)'
   ```

   Expected while an alert is open: one row per budget past 70 percent, such as `Horizon (mainnet)  70  453600  648000`.

2. Find what spent it. `upstreamUsage/{date}` shows the days, and the access log shows the routes and keys of the same period. Many requests from one key point at an integrator to talk to, or at a key whose rate limit to lower.
3. If the growth is real, move the upstream before it starts refusing: a paid plan, an API key, or a second provider in the list, set as [Provider outage](/runbooks/provider-outage) step 3 shows. Then raise the budget in `upstream-budgets.json` to match the new quota, with its source in this table, and deploy.
4. `upstream_budget_check_failed` in the log means the counts could not be read: see the [Firestore outage](/runbooks/firestore-outage) runbook if it repeats.
