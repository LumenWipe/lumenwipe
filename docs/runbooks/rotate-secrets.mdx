None of these secrets signs a Stellar transaction, so none can move funds. Each section lists what stops working and for whom.

**How each one is set.** Run every step in a shell started with `set -o pipefail`, so a failed command in a pipe never stores an empty version. Then check how each variable is bound:

```bash
gcloud run services describe lumenwipe-api --region us-central1 --format='yaml(spec.template.spec.containers[0].env)'
```

An entry with `valueFrom.secretKeyRef` is bound to Secret Manager: add a version (`... | tr -d '\n' | gcloud secrets versions add <secret> --data-file=-`) and rebind it with `--update-secrets=<VAR>=<secret>:<n>`. A secret value that is a plain environment variable is readable by anyone who can describe the service: bind it to a secret as part of the rotation, the same way. Never type a secret on the command line, where it lands in shell history and the process list; pipe it, or read it into a shell variable as below. Every update creates a revision that serves within about a minute; read the binding back after it.

## Admin token

`ADMIN_API_TOKEN` gates the operator-only `/admin/api-keys` routes.

**Blast radius**: operators only. The old token stops working the moment the new revision serves. Integrators and users see nothing.

1. Generate the token into a new version, never on screen: `openssl rand -hex 32 | tr -d '\n' | gcloud secrets versions add <admin-token-secret> --data-file=-`. Expected: `Created version [<n>]`.
2. Rebind it: `gcloud run services update lumenwipe-api --region us-central1 --update-secrets=ADMIN_API_TOKEN=<admin-token-secret>:<n>`. Expected: `Done.`
3. Confirm, passing each token as a header file so it never appears on the command line:

   ```bash
   bearer() { printf 'Authorization: Bearer %s' "$(gcloud secrets versions access "$1" --secret=<admin-token-secret>)"; }
   curl -s -o /dev/null -w '%{http_code}\n' -H @<(bearer <n>) "$API/admin/api-keys"
   curl -s -o /dev/null -w '%{http_code}\n' -H @<(bearer <previous n>) "$API/admin/api-keys"
   ```

   Expected: `400` for the new token (authorized, refused only for the missing `owner`), `401` for the old one.

4. Disable the previous version: `gcloud secrets versions disable <previous n> --secret=<admin-token-secret>`.

## Integrator sign-in secret

`INTEGRATOR_AUTH_SECRET` signs the wallet sign-in challenge and the session tokens of the self-service key page. At least 32 characters.

**Blast radius**: everyone signed in to the key page is signed out, and a challenge issued before the switch no longer verifies, so they sign in again. API keys themselves are untouched and keep working.

1. `openssl rand -hex 32 | tr -d '\n' | gcloud secrets versions add <integrator-secret> --data-file=-`, then `--update-secrets=INTEGRATOR_AUTH_SECRET=<integrator-secret>:<n>`. Expected: `Done.`
2. Confirm a new challenge is issued:

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' -X POST "$API/v1/integrator/auth/challenge" \
     -H 'content-type: application/json' -d '{"address":"<any G address>"}'
   ```

   Expected: `200`. Sign in on the key page with a testnet wallet: the keys list loads.

3. Disable the previous version.

## Static API keys

`API_KEYS` is a list of `label=key` pairs: the web app's own key, the deploy smoke key and any manually provisioned partner. Self-serve keys are rotated by their owners on the key page and are not covered here.

**Blast radius**: the holder of the rotated key only. Overlap the two keys so nobody sees a `401`.

1. **Add the new key next to the old one**, under the same label (two keys may share a label; metering counts them together). `API_KEYS` holds every static key, so it is always bound to a secret; if it is still a plain variable, bind it now. Build the new list in a shell variable, never on screen:

   ```bash
   NEW_KEY="$(openssl rand -hex 32)"
   CURRENT="$(gcloud secrets versions access <n> --secret=<api-keys-secret>)"
   printf '%s,<label>=%s' "$CURRENT" "$NEW_KEY" | gcloud secrets versions add <api-keys-secret> --data-file=-
   gcloud run services update lumenwipe-api --region us-central1 --update-secrets=API_KEYS=<api-keys-secret>:<n+1>
   curl -s -o /dev/null -w '%{http_code}\n' -H @<(printf 'Authorization: Bearer %s' "$NEW_KEY") "$API/v1/testnet/account/<a funded testnet address>"
   ```

   Expected: `Created version [<n+1>]`, `Done.`, and `200`.

2. **Move the holder to the new key**, piped:
   - the web app: `printf %s "$NEW_KEY" | vercel env add LUMENWIPE_API_KEY production` after removing the old value with `vercel env rm LUMENWIPE_API_KEY production`, then redeploy the production build;
   - the deploy smoke test: `printf %s "$NEW_KEY" | gh secret set API_SMOKE_KEY`;
   - a partner: through the channel agreed with them.

3. **Remove the old key**: add a version with the old pair removed from the list (read it, edit it in the shell variable, pipe it in as in step 1) and rebind it. Expected: `Done.`

4. Confirm the same `curl` with the old key answers `401` and with `$NEW_KEY` `200`; for the web app, a testnet close plan loads on the site. Then `unset NEW_KEY CURRENT` and disable the superseded versions.

## RPC and Horizon provider keys

Private providers authenticate with a header: `STELLAR_RPC_HEADER_NAME_<NET>` and `STELLAR_RPC_HEADER_VALUE_<NET>` for the first RPC URL, `_2` and `_3` suffixes for the later ones, and the same scheme under `PATH_ROUTING_API_HEADER_*` for the Horizon-compatible list. `SOROSWAP_API_KEY` and `OCTOPOS_API_KEY` are the conversion quote and position detection keys.

**Blast radius**: reads through that one provider. With a provider list, a provider whose key fails is answered with `503` and the client's retry moves to the next one ([Provider outage](/runbooks/provider-outage)); with a single provider, the network's reads fail until the new key is in.

1. Create the new key in the provider's console, keeping the old one active.
2. Paste the new value at a silent prompt, store it as a version and bind it:

   ```bash
   read -rs VALUE
   printf %s "$VALUE" | gcloud secrets versions add <provider-secret> --data-file=- && unset VALUE
   gcloud run services update lumenwipe-api --region us-central1 --update-secrets=STELLAR_RPC_HEADER_VALUE_<NET>=<provider-secret>:<n>
   ```

   Expected: `Created version [<n>]` and `Done.`

3. Confirm the provider answers:

   ```bash
   curl -s "$API/health/dependencies" | jq '.dependencies[] | select(.network=="<net>") | {upstream, state, lastErrorClass}'
   curl -s -o /dev/null -w '%{http_code}\n' "$API/health/deep"
   ```

   Expected: `"state": "up"` for `rpc` and `horizon` on that network, and `200` from `/health/deep`. Each probe result is cached for one minute (five for `paths` and `defi`), so wait that long after the switch. These routes spend provider quota; call them a few times, not in a loop.

4. Revoke the old key in the provider's console, then repeat step 3. Expected: unchanged.
