LumenWipe builds transactions on the server, but signing always happens in your browser. Your private key never reaches LumenWipe.

## Wallet

The default. Connect a wallet through Stellar Wallets Kit. The wallets the app offers are listed in [Supported](/reference/supported#wallets). The app hands the wallet an unsigned transaction and receives the signed one back, so the key stays inside the wallet.

While the wallet's prompt is open, the screen shows what it was asked to sign: where the account's balance goes when the transaction merges the account, the number of operations, and the first and last eight characters of the transaction hash. All three are read from the exact transaction handed to the wallet, so check that the wallet's own prompt matches before you approve. Mobile wallets, LOBSTR included, connect through WalletConnect and show the prompt in their app; a deployment without a WalletConnect project id says so under **Connect wallet**.

The app only says a wallet is connected once it has checked. A session kept from earlier in the flow is checked by asking the wallet for its account without opening anything; if the wallet cannot be asked that way, or answers with another account, the app shows **Reconnect wallet** instead. A wallet that does not report its network has to be confirmed as being on the page's network before it can sign, and a wallet on another network cannot sign at all. If the wallet signs with a different account than the one connected, or for the other network, the signature is refused before it is used, and the app names the account and lists the keys that can sign.

## Secret key

For keys that live in no wallet. The key is held in memory only for the length of the session. It is never written to storage and never sent over the network. It is wiped when the close completes, when you abort, when you leave the page, or when you click **Forget key**.

Anyone who has the key controls the account. Once a key is entered, the screen shows its public key (the first and last six characters) and whether it is a signer on the account being closed, with its weight. Once a transaction is waiting for more signatures, that standing comes from the signers read for it then, so a co-signer added after review is recognised. A key the account does not list, or lists with weight 0, cannot sign, and the sign button stays disabled with the reason next to it.

## Multisig accounts

When an account needs several signers to reach its threshold, connect wallets or enter keys one after another. Signatures accumulate on the same transaction until the threshold is met, then it is submitted. The screen always names the signer that will sign. Each time a transaction is still short of weight, the signer is cleared: a secret key has to be entered again if a later transaction needs it, and a connected wallet stays connected but is offered only for a transaction that still needs its signature. A signer that already signed a transaction cannot be asked to sign it again. Each transaction needs the full weight, so expect to sign once per transaction with each signer.

When extra signers exist, the plan removes them early. That collapses the rest of the close to a single key and releases each signer's reserve.

A transaction that removes signers and does not merge the account in the same transaction must carry the account's master key and reset the thresholds. Without both, the app submits nothing: the transaction would leave the master key as the only signer, with the merge still to come. A close that merges in the same transaction can be signed by the co-signers alone.

## hash(x) signers

A hash(x) signer is a key that is the SHA-256 hash of a secret value. To satisfy one, enter the preimage as a hex string. LumenWipe checks that it hashes to the signer's key before using it, and rejects it otherwise.

Entering the preimage publishes it. A hash(x) signature is the preimage itself, it is not bound to one transaction, and the signer stays on the account after it is used, so anyone who reads it can use that signer's weight until the signer is gone. The app therefore attaches a preimage only to a transaction that removes that same signer. Any other step needs another signer.

## Pre-authorized transaction signers

A [pre-auth signer](/reference/glossary#pre-auth-signer)'s key is the hash of one specific transaction, authorized in advance. It contributes weight only when that exact transaction is submitted, never by signing something new.

LumenWipe builds a fresh transaction every round, so a pre-auth signer will almost never match it. The only way to use one is to paste the exact pre-authorized transaction [XDR](/reference/glossary#xdr).

After you paste it, **Review transaction** decodes it and lists its source account, every operation in order (an operation the app does not describe is listed as "Unrecognized operation" with its type, and a contract call with every argument), the merge destination, the memo with its type, the fee, the sequence number and when it can land. Only a second click, **Submit pre-authorized transaction**, sends it, after the same checks as before. Once the network confirms it, the app shows its hash with an explorer link and continues the close on its own: it reads the account again and either finishes, if the transaction merged the account, or asks for the next signature. Retrying that step never sends the pre-authorized transaction again. If the network gives no clear answer, the transaction is held as unconfirmed, like any other of the close, and nothing more can be signed until **Check again** settles it.

<Warning>
  LumenWipe did not build or verify a pasted pre-authorized transaction the way it does every other
  one. Review it yourself before you submit it. The app shows this warning every time.
</Warning>

## What you are asked to check

Before each signature, the browser shows what the transaction does. The check covers where the funds go, any [memo](/reference/glossary#memo), and that only removals and conversions are included. Read the destination before you confirm.
