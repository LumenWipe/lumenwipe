`runClose` is a pure, dependency-injected runner. It fetches each round, verifies every transaction before signing, signs, and submits only once the signing weight is enough, repeating until the close is done. The LumenWipe web app drives its own closes the same way.

```ts
import { runClose } from "@lumenwipe/sdk";

await runClose({
  planHash: plan.planHash,
  getTransactions: ({ planHash }) =>
    client.closeTransactions({ source, destination, decisions, planHash }),
  verify: (tx) => verifyCloseTransaction(tx, { source, destination }),
  requiredWeight: () => 1,
  sign: async (tx, xdr) => ({ xdr: signWithMyKey(xdr), weight: 1 }),
  submit: async (tx, xdr) => (await client.submit(xdr)).hash,
});
```

## Dependencies

| Dependency        | Description                                                                                                                                     |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `getTransactions` | Fetches the next round, usually `client.closeTransactions(...)`. Pass on the `planHash` it is given.                                            |
| `verify`          | Checks one transaction against your own inputs. It must throw on any mismatch. It may be async.                                                 |
| `requiredWeight`  | The signing weight this transaction needs, from its operations and the account's real thresholds.                                               |
| `sign`            | Signs the XDR, which may already carry signatures, and returns the new XDR with its accumulated weight.                                         |
| `submit`          | Submits a transaction that meets its weight and resolves to the hash.                                                                           |
| `onConfirmed`     | Optional. Called with the transaction and its hash after each confirmation.                                                                     |
| `onProgress`      | Optional. Called with progress messages.                                                                                                        |
| `planHash`        | Optional. The `planHash` of the plan the user reviewed. Sent with each fetch until the first transaction of the run confirms, then never again. |
| `sleep`           | Optional. Waits the given milliseconds before a re-fetch. Defaults to a timer; inject one in tests.                                             |
| `maxRounds`       | Optional. Overrides the round bound. By default the bound follows the API's `remaining.steps` (capped at 200).                                  |

`verify` is where the security of your integration lives. `runClose` guarantees it runs before every signature, but only your implementation decides what it accepts. Two signing guards of the LumenWipe web app are not part of `runClose`, so your `sign` and `submit` need their own: never attach a hash(x) preimage to a transaction that does not remove that same signer, and never submit a transaction that removes signers without an `account_merge` unless the master key has signed it and the same transaction lowers every threshold to 1 or below. See [Verification](/sdk/verification).

`runClose` resolves with `{ mergeConfirmed }`. Without `reconcile` it is always `false`: returning then says only that the API asked for no more calls, and a transaction's `covers` is API metadata. Do not tell a user the account is closed until you have established the merge yourself, from the envelope you signed and a confirmed lookup of its hash.

## Unknown outcomes

Without `reconcile`, a failed `submit` is thrown as it is. Pass `reconcile` and `runClose` settles an unknown outcome by hash instead:

```ts
await runClose({
  ...deps,
  prepare: async (tx, xdr) => addCoSignatureOrSponsorship(tx, xdr),
  reconcile: {
    hashOf: (xdr) => TransactionBuilder.fromXDR(xdr, passphrase).hash().toString("hex"),
    closesAccount: (xdr) => envelopeMergesAccount(xdr, source),
    validUntil: (xdr) => envelopeMaxTime(xdr),
    lookup: (hash) => client.getTransaction(hash),
    onSubmission: (submission) => saveSomewhereDurable(submission),
    unresolved: loadFromSomewhereDurable(),
  },
});
```

`hashOf` must run on your side, on the exact final envelope, with your own network passphrase. The SDK has no Stellar dependency, so it never computes a hash, and it never takes one from the API: an answer naming any other hash leaves the outcome unknown.

Everything but a `4xx` from `submit` counts as unknown. `runClose` then sends the same bytes again, at most `SUBMIT_RESEND_ATTEMPTS` (2) times, `SUBMIT_RESEND_DELAY_MS` (5 seconds) apart. `prepare` runs once per transaction, so a resend never repeats a co-signature or a sponsorship. If that settles nothing it looks the hash up, then throws `CloseOutcomeUnknownError` with a `submission` to pass back as `unresolved`, or `CloseTransactionFailedError` if the transaction failed on the ledger.

An `unresolved` submission is looked up, never sent. With `reconcile`, `onConfirmed` receives `covers` naming a merge only when `closesAccount` parsed one, and `mergeConfirmed` is `true` only for such a merge confirmed under your own hash. A confirmed merge ends the close, and `account_not_found` alone never does: it counts only when the merge's own hash is confirmed. `not_found` stays unknown until `validUntil` plus `SUBMISSION_GIVE_UP_MARGIN_SECONDS` (120) has passed by both your clock and the ledger close time in the lookup, and then the close returns to a fresh round. Persist only what `UnresolvedSubmission` holds, never the signed envelope.

## Multisig and partial signing

A round can change the account's signers and thresholds: signer normalization removes extra signers and lowers the thresholds. Judge `requiredWeight` and `sign` against the response's `sourceAccount`, the read the round was built from, with each confirmed `SetOptions` applied on top as its transaction lands. Against an earlier read, a later transaction asks for weight the account no longer needs, or for a signature from a key it no longer has, which the network refuses.

If `sign` returns a weight below `requiredWeight`, `runClose` throws `InsufficientSignatureWeightError`. Its `pending` property holds everything needed to continue with a different signer on the same envelope. Pass it back as the second argument to resume without re-fetching, which would discard collected signatures:

```ts
import { runClose, InsufficientSignatureWeightError } from "@lumenwipe/sdk";

try {
  await runClose(deps);
} catch (error) {
  if (error instanceof InsufficientSignatureWeightError) {
    await runClose(depsWithNextSigner, error.pending);
  } else {
    throw error;
  }
}
```

If the API refuses a round as `state_changed` (the account changed between its read and its build), `runClose` asks for that round again, at most `STATE_CHANGED_REFETCHES` (2) times and each time after waiting `STATE_CHANGED_REFETCH_DELAY_MS` (3 seconds, about one ledger close), because each call re-reads the account and a read provider can lag a transaction that just confirmed by a ledger or two. If the round is still refused, or it was refused against the reviewed `planHash` (the plan itself is stale, so it is not asked for again), it throws `CloseStateChangedError`. Nothing was submitted for that round: plan the close again, have the user review the new plan, and run the close from it.

If a close does not finish within the round bound, or the API says another call is needed but returns no transactions, `runClose` throws `CloseDidNotConvergeError`. Its `rounds`, `bound` and `reason` (`round_limit` or `empty_batch`) say why, and its message is plain language. Nothing is lost: run the close again and it picks up where it stopped.
