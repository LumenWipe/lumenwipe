<Warning>
  The SDK does not verify or sign anything. Never sign a transaction returned by the SDK without
  `@lumenwipe/verify` or an equivalent check of your own.
</Warning>

Closing an account is irreversible: it merges every remaining lumen into one destination. Every transaction the SDK returns is unsigned XDR built by the API from the data you provided. Before signing, your code must independently confirm that the transaction does exactly what the user asked.

## Use `@lumenwipe/verify`

`@lumenwipe/verify` is the verifier the LumenWipe web app runs before every signature, as a package. It is compiled from the web's own [`verify.ts`](https://github.com/LumenWipe/lumenwipe/blob/main/apps/web/lib/stellar/verify.ts), not ported, so there is one implementation. A shared set of conformance vectors runs against the package and against the web verifier in CI.

```bash
npm install @lumenwipe/verify @stellar/stellar-sdk@17.4.0
```

`@stellar/stellar-sdk` is a peer dependency, pinned to the version the web verifier is tested with, and is never bundled.

Pass it as `verify` to [`runClose`](/sdk/run-close):

```ts
import { LumenWipeClient, runClose } from "@lumenwipe/sdk";
import { exitExpectations, verifyCloseTransaction } from "@lumenwipe/verify";

const account = await client.getAccount(source); // the read the user reviewed

await runClose({
  // getTransactions, requiredWeight, sign, submit as usual
  verify: (tx) =>
    verifyCloseTransaction({
      unsignedXdr: tx.xdr,
      network: "testnet",
      expected: {
        source,
        destination, // typed by the user
        nativeBalance: account.nativeBalanceLumens,
        memo: null, // the memo the user confirmed, and its type
        memoType: null,
        claimTrustlineAssets: [],
        accountSigners: account.signers,
        accountThresholds: account.thresholds,
        transfers: {}, // the user's per-asset choices
        tokenTransfers: {},
        classicConversions: {},
        tokenConversions: {},
        ...exitExpectations(account, "testnet"),
      },
    }),
});
```

`verifyCloseTransaction` returns only when the transaction may be signed, and throws `VerificationError` otherwise. It is synchronous and reads no network.

### Where each input comes from

| Input                                                                   | Source                                                                                                                                     |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `destination`, `memo`, `memoType`                                       | What the user typed and confirmed.                                                                                                         |
| `transfers`, `tokenTransfers`, `classicConversions`, `tokenConversions` | The user's per-asset choices, with the balance or quote they were shown as the floor. Pass `{}` for none.                                  |
| `claimTrustlineAssets`                                                  | The `CODE:ISSUER` of each claimable balance the user chose to claim into a new trustline.                                                  |
| `source`, `nativeBalance`, `accountSigners`, `accountThresholds`        | The account read the user reviewed (`client.getAccount`). Empty signers fail closed.                                                       |
| The DeFi fields                                                         | `exitExpectations(account, network)`, from the same read and the contract registry bundled in the package. With no read, every exit fails. |

Never take an input from the transaction under verification or from its `intent` summary. The values from the account read come from the same API that builds the transaction, so they catch a builder bug or a partial compromise, not an API that keeps both consistent.

### What the package decides on its own

Whether the destination is a listed exchange, whether it needs a memo and of which type, and whether the merge must go through the shared mediator are not inputs. The package derives them from the exchange registry bundled in its release. It never fetches the copy the API serves:

- An exchange listed after the release you installed is checked as a plain wallet, so a direct merge to it passes with whatever memo the user typed. Upgrade on every release.
- Once the bundled registry's `validUntil` date passes, every close to a listed exchange is refused until you upgrade.

It also reads the system clock: a transaction valid for more than 900 seconds from now is refused.

### Conformance vectors

The package ships `vectors/close-v1.json`: accepted and rejected transactions with the full input for each, the clock to set, and the exact `VerificationError` message for each rejection. Every rejection is one named mutation of an accepted vector, and every key in the file is public. Run them against your own verifier, or against a wrapper around this one.

## Why

LumenWipe's architecture puts the trust boundary at the signer. The API builds the bytes, and the client decides whether to sign them. If a compromised or faulty API could choose what you sign, it could divert funds. Your own check removes that risk.

## What to check if you write your own

Decode the XDR yourself and compare it against **your own inputs**, never against values from the API response alone. At minimum:

- The transaction source is the account being closed, and every operation is sourced from it.
- The account merge goes only to the destination the user stated. For an exchange, the merge goes to the shared mediator, and a forward payment from the mediator goes to the user's stated address in XLM for at least the observed balance.
- Payments are only a return to the issuer, a transfer matching the user's own asset, destination, and amount choice, or the mediator forward.
- Conversions are to self or to native, with a positive destination minimum.
- Removals only: trustlines, data entries, and offers.
- `SetOptions` never adds a signer or raises a threshold.
- The memo matches what the user supplied.
- No unknown operation type. Reject anything you do not recognize rather than signing it.

## Mediated closes: the destination is yours to check

The API's co-sign endpoint checks the **structure** of the mediated pair, not where it pays. It caps the forward at the merged balance it reads at co-sign time, but it accepts a forward to any address other than the mediator, because it cannot know which exchange address the user meant. It does refuse a forward without a memo to a listed exchange that requires one or to an account whose `config.memo_required` data entry is set (SEP-29), and a memo of the wrong type to a listed exchange, but it cannot know which memo value the user meant. In the LumenWipe web client, `verify()` makes that check with the address the user typed. An integration that calls the API or the SDK directly has no such check unless it writes one, so for a mediated close confirm, from your own inputs:

1. The destination the user entered needs the mediator (a known exchange that cannot receive a merge): `requiresMediator(destination)` from `@lumenwipe/verify` answers this from its bundled registry. Otherwise the merge must go straight to the user's address and the mediated shape is refused, so an intermediary the API names cannot be slipped into a close to a plain wallet.
2. The transaction source is the account being closed, with exactly two operations: an `accountMerge`, then a `payment`.
3. The merge is sourced from the account being closed (explicitly, or by inheriting the transaction source).
4. The payment is sourced from the merge's destination, the account the merge pays into.
5. The payment goes to the exchange address the user entered.
6. The payment is in native XLM.
7. The payment's amount is at least the native balance you observed, less a small fee tolerance (the web client allows 0.01 XLM).
8. The memo and its type match what the user entered and what the exchange requires.

Pinning the mediator's address in place of step 4 proves which account receives the merge, not that the payment moves the balance on. The [threat model](/threat-model#integrator-responsibility-for-a-mediated-close) states this responsibility and the known forward window (`S4a.Elevation.1`) next to it.

The `intent` field on a transaction is the API's own summary. Do not use it as a check.

## Reference implementations

- `@lumenwipe/verify`, above, is the web client's verifier as a package.
- [`assertCloseIntent`](https://github.com/LumenWipe/lumenwipe/blob/main/apps/web/lib/stellar/verify.ts) in the LumenWipe web client is the source it is compiled from.
- The [headless example](/sdk/headless-example) wires the package into `runClose`.

Whatever you write, pass it as `verify` to [`runClose`](/sdk/run-close) so it runs before every signature.
